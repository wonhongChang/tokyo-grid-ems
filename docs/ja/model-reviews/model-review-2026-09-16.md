## 4. 候補検証と却下理由

### A. 気象入力感度の平均化

未来の予報気温だけを±0.5°Cまたは±1.0°C変更し、派生特徴量を再計算して元のrawと平均しました。実測気温は維持しました。校正済みの気象誤差分布ではなく、限定的な感度実験です。

- 8/14〜9/10のD0 origin 28件と9/14〜16の実行26件を復元し、54/54のbaseline再現チェックを通過しました。
- 28日間の正のlead 639行でraw MAEは**1385.9 → 1392.2 / 1391.6**。営業日・非営業日とも悪化しました。
- 直近実行の未来297行は1118.6 → 1109.6 / 1117.4でしたが、過去区間では改善しませんでした。複数発表時点を含むため日次表示線MAEではありません。
- **却下:** raw段階で悪化したため、全後処理replayや運用反映には進めませんでした。

### B. 既に低い予測へのcooler-day prior制限

既存のlag過熱由来の負の補正量を、予測と同営業区分anchorの正の差以内に制限しました。重複した下方補正を減らす候補です。

- 8/19〜9/16の保存記録から対象補正が有効な実行10件を見つけ、10/10のbaselineを完全再現しました。
- 0〜2時間の一意な日付・時刻15対象では、9/16 MAEが550.7 → 494.6、9/10が705.6 → 461.5へ改善しました。
- しかし実績のある正のlead 215行全体は**1002.9 → 1032.6**へ悪化しました。9/10は1315.6 → 1483.1となり、一部の日中は有効な下方補正がなくなって約700MW悪化しました。
- **却下:** 近距離の改善だけで全日適用や既存priorの廃止を正当化できません。

## 5. 採用したレポート修正

9/15入力では、火曜日08時の誤差を時刻だけで営業区分遷移guardに結び付け、16〜17時には明確な実績低下・予測反発がないのに夕方capを推薦する規則を確認しました。

1. 午前はlag・同区分・気象・補正段階を比較する調査候補にします。営業区分遷移の説明には明示的なmismatch根拠を要求し、その事実だけで原因は確定しません。
2. 夕方低下capの自動候補には、正の誤差・実績低下・予測上昇を同時に要求します。
3. 韓国語・日本語レポートの生成補完文に英語が混ざる経路を修正しました。
4. レポート再生成コマンドをモデルreplayコマンドとして提示する項目を削除しました。

ネットワークを遮断した関連テスト**74件が通過**。実際の9/15入力でも三言語の文脈をオフライン再構築し、誤推薦の除去を確認しました。有料AI再生成や総合品質点数の保証ではありません。既存の公開JSONは上書きしていません。[AIレポートガードレール](../ai-report-guardrails.md)にも反映しました。

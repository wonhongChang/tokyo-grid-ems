# D-1 갱신 중심선: 승인 후에만 실행하는 제한 발행

정책 `d1-point/1:raw:updates`. 기존 LightGBM 가중치와 최초 D-1 발행은 유지한다. 같은 대상일의 최초 적격 D-1이 공개됐다는 증거가 있을 때만 이후 D-1 중심선을 같은 실행의 원천 q50으로 바꾼다. 별도 학습·기상 요청·가상 당일 실측은 없다. Same-day, 원래 수준 보정 상태의 refresh, 모델 메타데이터, 일정은 기존 경로다. 상태·가드의 대조 결과는 계속 스냅샷에 기록한다. 폭 추정은 의도적으로 기존 정책이 소유한다. 새 정책에서 95% 포함이 보장되는 것은 아니다.

**기본 설정은 꺼져 있다.** 운영 코드 릴리스와 날짜 활성화는 별도 절차다. R2와 공유하는 `config.yaml`을 수정하지 않는다. 승인 후에만 로컬 `data/raw/.d1-point/trial.json`과 GitHub Actions repository variable `TOKYO_GRID_EMS_D1_TRIAL`에 같은 JSON을 사용한다. 로컬 파일과 발행 증명은 Git·Pages에 포함하지 않는다. 기존 기록을 재생성하지 않는다.

```json
{"policy":"b42c523a9775376043865d4132bf2e8b30432ff89ed26e2dea8501c090c0e2f1","targets":["2026-11-30","2026-12-03","2026-12-05"]}
```

1. 승인된 세 대상일만 허용하며, 실제 D-1 발행일은 각각 11/29, 12/2, 12/4 JST다. 스위치에서 날짜를 빼면 그 날짜만 중지한다. 허용되지 않은 날짜가 들어간 설정은 전체를 거부한다. 12/1 D+7 평가와 별개다.
2. GitHub Intraday와 Manual ETL은 복원에 사용한 공개 data ref로 선행 발행을 확인한다. Windows 예약 ETL은 전용 launcher가 공개 원격 SHA로 같은 준비 스크립트를 호출한다. 현재 운영 체크아웃을 이동하지 않고 ETL 컨테이너에만 읽기 전용 코드 마운트를 제공한다. 기존 ETL의 실행 시각, 수집·발행 절차와 Shadow 서비스는 바꾸지 않는다. 실제 공개란 이 정책에서는 **공개 Git data 브랜치에 오른 발행**으로, Pages 배포 완료 시각을 대신하지 않는다. 아래는 수동 확인 예다.

   ```powershell
   python -B scripts/prepare_d1_receipt.py --repository . --ref refs/remotes/origin/data --target 2026-11-30
   ```

   스크립트는 fetch하지 않는다. 공개 커밋에 담겼던 최초 origin의 SHA와 현재 ETL 입력 트리의 같은 파일을 대조한다. 기존 Docker bind `data/raw` 아래 날짜별 JSON 하나만 전달하고 CSV 수집·예측 입력으로 사용하지 않는다. 45일 이력, 모델 파일 복제, Docker 안의 Git, 추가 네트워크 연결이 필요 없다. 설정 누락·대상일 불일치·증명 미준비·시각 역전·SHA/기반정책 불일치는 기존 정책으로 처리한다. 최초 발행 자체가 애초에 다른 정책이었다면 해당 커밋 트리에 호환되는 앞선 스냅샷도 있어야 한다.
3. 첫 발행은 기존 fingerprint, 이후 적격 D-1은 새 fingerprint와 `d1PointPolicy`가 있어야 한다. `series[].forecastMw`와 `peak`가 실제 표시값이고 `intervalReferenceForecastMw`는 **같은 실행의 기존 정책 대조값**이다. `intervalCalibration.servingPolicyFingerprint`는 구간 추정기의 기존 기준을 가리킨다. 산출물의 루트 fingerprint와 목적이 다르다. 새 D-1 시리즈를 구간 추정에서 기존 발행처럼 혼입하지 않는다. 실측 확정 전에는 채점하지 않는다.

   ```powershell
   python -B scripts/check_d1_trial.py --repository . --ref refs/remotes/origin/data 2026-11-30 2026-12-03 2026-12-05
   ```

4. 발행 당일에는 의도한 대상일·관측 전 최초 발행·이후 적용 건수, 동일한 공개 JSON/스냅샷/피크, 정상 Same-day로의 복귀를 먼저 본다. 적격 갱신인데 적용 건수가 0이면 성공으로 세지 말고 증명을 확인한다. 늦은 첫 당일 발행에서 이미 실측이 들어온 시간은 정직하게 D-1 공개값으로 동결될 수 있다. H22를 온종일 새로 발행하지 못한 날은 다음 날 잔차 이월도 달라질 수 있으므로 해당 일자는 분리하고 확대하지 않는다.
5. 잘못된 대상·미래/불일치 증명 사용·당일 미래 중심선 또는 구간 기준선 혼선·공개 자료 불일치 시 즉시 중단한다. 확정 후 기준선과 짝지어 전체/17:30 MAE, 비영업일·16~18시, 최악 오차와 구간 포함률을 검사한다. 특히 최대 절대오차 +500 MW 초과, 구간 포함률 −2%p 초과 하락, 취약 구간 +5% 초과 악화는 더 넓게 적용하지 않고 조사한다. 세 날짜는 첫 운영에서 두 발행자·주중/비영업일·복귀가 정상인지 볼 범위이지, 미래 일반화가 통계적으로 증명되는 최소 일수는 아니다. 결과를 보고 승인 없이 기간을 연장하지 않는다.
6. **즉시 롤백:** 로컬 스위치 파일과 GitHub 변수 모두를 제거하거나 각각 `{"targets":[]}`로 바꾼다. 코드 재배포나 공유 모델 설정 변경은 필요 없다. 진행 중인 발행을 소급 취소하는 것은 아니므로 첫 비활성 발행의 중심선·지문을 확인한다. 구간 대조값을 읽는 호환 코드는 그대로 두므로 활성일에 남은 스냅샷 때문에 기존 구간 이력이 초기화되지 않는다. 과거 공개값·봉인을 지우거나 모델을 재학습하지 않는다.

### 사후 확인

`D-1 limited release audit`는 기존 Intraday 성공 후 지정한 확인일에만 읽기 전용으로 실행되며, 지연 확정 시 수동으로도 실행할 수 있다. 결과는 해당 Actions 실행의 `d1-trial-scores` 아티팩트(90일)다. 로컬 재현에는 출력의 공개 commit과 동일한 ref를 사용한다. 최초 공개, 17:30 이전 마지막 공개, 마지막 D-1을 구별한다. 모든 D-1의 MAE/RMSE/절대오차 P95·최댓값, 95% 구간 포함률과 발행 수정 효용(수정 전 절대오차 − 수정 후 절대오차)을 같은 실제값·같은 실행의 Champion과 짝짓는다. 구간 대조는 동일한 폭을 기존 중심선으로 평행 이동한 것이다. 대상일 안에서는 반복 발행을 포함하고, 날짜 간에는 동등한 비중을 둔다. 최초 당일의 지문·실측 보유 수와 자정 전환 효용은 별도로 본다. 당일 반사실 전체 곡선이 기록되지 않았다면 수치 동등성을 주장하지 않는다.

Windows 설치본은 보호 checkout 밖의 고정 release 사본을 참조한다. launcher의 `-CheckOnly`는 실제 ETL·발행 없이 컨테이너 내 코드와 스위치를 표시한다. 원본 작업 action은 설치 전 별도 보관한다. 정책 비활성화 후에도 과거 구간 대조값 해석은 유지하고, 본체에 호환 코드가 통합된 뒤에만 wrapper를 해제한다. 세 날짜가 끝나면 allowlist는 자동 만료와 같은 효과를 가지며 영구 전환은 자동으로 이루어지지 않는다.
